# C1. Переход задачи Jira в работу

## Назначение

Добавить команду `jira transition <ключ> [--dry-run | --no-dry-run]` и подключить первые две стадии `flow`. По завершении `ticket` известен ключ задачи, а `in-progress` закрывается после подтверждения статуса в Jira или пропуска с записанной причиной. Требования взяты из роадмапа Task-flow и его общей спецификации.

## Архитектура

Jira CLI переиспользует загрузку настроек и авторизованный профиль браузера из `create`. Сценарий перехода открывает карточку по ключу на настроенном Jira, проверяет сессию и фактический статус, ищет доступное действие, выполняет его и проверяет статус после повторного чтения карточки. Статусы переданного рабочего процесса определены в `JIRA_STATUS`. Для перехода по умолчанию используется `JIRA_STATUS.IN_PROGRESS` с английским эквивалентом `In Progress`. В меню Jira в первую очередь проверяется метка статуса назначения. Проект может задать другой целевой статус или точное имя действия для классической панели и для выбора между несколькими переходами к одной цели. Сравнение подписи точное после нормализации регистра и пробелов. При неоднозначном совпадении команда сообщает об ошибке.

Если нужный статус уже выставлен, команда сообщает об этом и не выполняет переход повторно. В пробном режиме команда проверяет доступность перехода, оставляет окно для инспекции по соглашению `create --dry-run` и не активирует действие, которое может сразу изменить задачу. Флаг командной строки имеет приоритет над `jira.dryRun`. Сессия, закрытая без подтверждённой смены статуса, отсутствие задачи, недоступный переход, отказ Jira и таймаут дают диагностируемый ненулевой код. Успешный выход отдаёт JSON с ключом, URL, статусом операции (`transitioned`, `already-in-progress` или `dry-run`) и прочитанным статусом карточки. Диагностика выводится отдельно в stderr.

Вариант с прямым Jira REST API требует отдельной схемы авторизации и обходит уже работающий профиль. Вариант, в котором агент вручную запускает Jira CLI и записывает результат, требует от агента проверять успех. Выбран существующий браузерный CLI как единственный исполнитель операции, а `flow` проверяет его структурированный результат.

## Определение задачи

`flow start` принимает явный ключ или HTTPS-ссылку на карточку с конечным путём `/browse/<ключ>`, в том числе под контекстным путём Jira. При настроенном `jira.baseUrl` входная ссылка должна указывать на этот экземпляр. Из ссылки сохраняются ключ, адрес экземпляра и его контекстный путь. Перед операцией `flow` и Jira CLI сверяют экземпляр с `jira.baseUrl`. Карточка открывается по проверенной конфигурации Jira. Некорректный явный аргумент даёт `blocked` с причиной.

При отсутствии аргумента `flow start` ищет ключ в имени текущей ветки. Если задан `ticketPrefix`, он ограничивает поиск в имени ветки. Контекст разговора передаёт сам агент как явный аргумент. При отсутствии однозначного ключа команда возвращает `needs-input` с вариантами передать ключ или ссылку либо подготовить задачу через `jira-writer`. До получения ключа состояние не создаётся. Режим `--no-tracker` сохраняет поддержку локального идентификатора и пропускает `in-progress`. Для старых состояний без отметки трекера доступен явный пропуск с причиной. Если старый идентификатор является ключом Jira, `flow next --task <ключ> --confirm-jira` подтверждает привязку и сохраняет прежние стадии.

## Переход между стадиями

После записи нового состояния `ticket` закрыта с доказательством в виде ключа. Вызов `flow next` на стадии `in-progress` запускает Jira CLI из корня проекта. `flow start` и `flow status` только читают или создают локальное состояние и не меняют Jira. `flow next` использует настройки пробного запуска, заданные проектом. При `dry-run` он сообщает, что стадия остаётся открытой, и подсказывает явную команду `flow next --task <ключ> --no-dry-run`. Успешного кода выхода Jira CLI недостаточно: ключ и подтверждённый статус операции должны совпасть с ожиданиями. Тогда доказательство сохраняется, ответ `flow` показывает следующую стадию, а очередной `next` отдаёт пакет для спецификации.

Операция записи использует существующую блокировку задачи. Ошибка Jira, неожиданный ответ или пробный запуск оставляют стадию открытой. Если процесс прервался между изменением в Jira и записью состояния, повторный запуск закрывает стадию после чтения уже установленного статуса. `flow skip in-progress --reason <причина>` сохраняет причину и переводит задачу к спецификации без изменения Jira.

## Критерии приёмки

- Команда Jira проходит через карточку тестовой Jira, меняет статус и подтверждает его. Повторный и пробный запуски не отправляют переход. Ошибки сессии, недоступного действия и неподтверждённого статуса различимы.
- `flow` обрабатывает ключ, ссылку, имя ветки и отсутствие однозначного ключа. Сценарий с заглушкой Jira CLI доказывает, что только подтверждённый переход закрывает стадию и что `next` не повторяет операцию после закрытия.
- Действующие тесты Jira и `flow` проходят на Node 24. Сценарий ручной проверки описывает пробный вызов и переход на явно выбранном тестовом тикете реального Jira.

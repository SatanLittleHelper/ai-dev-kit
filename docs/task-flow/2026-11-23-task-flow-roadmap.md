# Роадмап: Task-flow

## Контекст

Цель — жёстко зафиксировать флоу разработки задачи (тикет → «в работе» → спека → тест-план → план → реализация → polish → локальный тест → ревью в Plannotator → PR) так, чтобы он одинаково выполнялся в Claude Code, Codex, opencode и других агентах и не зависел от того, взята задача из роадмапа или одиночная. Всё, что можно решить кодом, решает TypeScript-оркестратор `flow` с понятным CLI; агент остаётся там, где нужно творчество или суждение. Полная архитектура, стадии, CLI и границы гарантии — в согласованной спеке `docs/superpowers/specs/2026-11-23-task-flow-design.md`.

Сейчас порядок документов описан текстовыми правилами в `rules/core.md`, `rules/orchestrator.md` и `roadmap/references/executing-checkpoints.md`; ничто не проверяет, что агент их выполнил. Polish — мод только для Claude, локальное тестирование и ревью в Plannotator выполняются по запросу, статус задачи в Jira не меняется.

Ограничения: гарантия только локальная (без CI и без коммита состояния в ветку); `flow` не запускает LLM сам; существующие skills и правила для работы вне задачи (идея без тикета, написание роадмапа, Jira-черновик) сохраняются; после каждого шага кит остаётся работоспособным. Поэтому переключение `core.md` и `orchestrator.md` на `task-flow` делается последним шагом: пока `flow` покрывает не все стадии, действуют прежние правила, а `task-flow` в промежутке подключается как необязательный. Номера тикетов пока `TBD`, имена команд предварительные. Спеки, тест-планы и планы готовятся при взятии конкретного шага.

Оценки грубые: один разработчик, знакомый с репозиторием; день — около 6 часов сосредоточенной работы. Оценка с агентом включает проверку человеком и доработки.

## Целевое устройство

Оркестратор `plugins/kit/tools/flow/` хранит состояние задачи в `tmp/flow/<ticket>.json`, ведёт её по стадиям строго по порядку, выдаёт агенту рабочий пакет стадии (`flow next`), сам проверяет и показывает документы в Plannotator (`flow submit` / `flow wait`) и закрывает стадию только при проверяемых доказательствах. Тонкий skill `task-flow` и блок в `AGENTS.md` дают единый вход для любого агента; хуки Claude и Codex и git-хук `pre-push` — необязательное усиление.

## Порядок выполнения

Ядро: A1 → A2 → A3; A4 (устойчивость, по итогам ревью A1) идёт после A1 независимо. Plannotator-часть B1 → B2 идёт после A2. Независимо стартуют C1 (Jira `transition`) и D1 (skill `polish`). Хуки E1–E3 после A3 и A1. F1 собирает все стадии в `flow` и требует B1, B2, C2, D1. F2 — финальное переключение правил и роадмапа на `flow`. Порядок списка отражает приоритет, а `depends` — только обязательные зависимости.

## Задачи

- [x] A1 — Ядро состояния и стадий (Jira: TBD) (est: 1–3д / agent: 0.5–1.5д)
  - Объём: каркас CLI `plugins/kit/tools/flow/` (Node 24, без зависимостей), файл состояния `tmp/flow/<ticket>.json`, машина из 10 стадий со строгим порядком, команды `start`, `status`, `skip --reason`, ответы `ok` / `blocked` / `needs-input` в JSON и `--text`, сброс стадий при изменении хеша согласованного документа.
  - Готово, когда: переходы и отказы покрыты `node --test`, пропуск стадии без причины невозможен, `status` восстанавливает положение после «потери контекста».

- [ ] A2 — Рабочие пакеты и валидаторы (Jira: TBD) (est: 2–3д / agent: 1–1.5д) (depends: A1)
  - Объём: `flow next` для стадий `spec`, `test-plan`, `plan`: вычисление тикета, слага, дат, путей черновика и цели, детект стека по `package.json`, подстановка нужных правил текстом, подсчёт `### Task N:` для «небольшой задачи»; валидаторы документов (русский язык, заголовки и чекбоксы плана, ссылки плана на ID тест-плана).
  - Готово, когда: `next` отдаёт полный пакет без обращения агента к файлам правил, валидаторы отклоняют некорректные документы с понятной ошибкой, всё покрыто тестами.

- [ ] A3 — Skill task-flow (опциональный вход) (Jira: TBD) (est: 1–2д / agent: 0.5–1д) (depends: A2)
  - Объём: skill `kit:task-flow` с циклом «`status` → `next` → работа → `submit` → `wait`»; для стадий, которых в `flow` ещё нет, явно указывает действующие прежние правила. `core.md` и `orchestrator.md` пока не трогаем.
  - Готово, когда: skill проходит `tests/layout.test.mjs`, работает как необязательный вход, прежние маршруты не нарушены.

- [ ] A4 — Устойчивость чтения состояния и CLI (Jira: TBD) (est: 0.5–1д / agent: 0.25–0.5д) (depends: A1)
  - Объём: итоги ревью A1. `flow status` без `--task` не должен блокироваться посторонним или повреждённым `*.json` в `tmp/flow/`: такие файлы пропускаются либо отказ называет файл и подсказывает `--task <id>`; структура `stages` в файле состояния проверяется (имена из списка стадий, допустимые статусы), иначе `blocked`, а не исключение. CLI отклоняет неизвестные флаги, лишние позиционные аргументы и флаги без значения (`--task`, `--reason`) с `blocked`. Решить контракт путей доказательства (от корня репозитория или от текущей папки) вместе с появлением команды закрытия стадии.
  - Готово, когда: перечисленные случаи покрыты тест-кейсами, согласованными в тест-плане шага, и не ломают тесты A1.

- [ ] B1 — Согласование через Plannotator: submit и wait (Jira: TBD) (est: 2–3д / agent: 1–1.5д) (depends: A2)
  - Объём: `flow submit` валидирует и запускает `plannotator annotate --gate --json` с `PLANNOTATOR_ANNOTATE_HISTORY=1` в фоне, возвращает `pending`; `flow wait` возвращает `approved`, `annotated` (структурно) или `dismissed`; запись в целевой путь и удаление черновика только после `approved`; «no feedback» не считается согласованием.
  - Готово, когда: поведение покрыто тестами с заглушкой Plannotator, повторные `wait` не теряют результат, правки согласованного документа сбрасывают стадию.

- [ ] B2 — Цикл doc-review внутри flow (Jira: TBD) (est: 1–2д / agent: 0.5–1д) (depends: B1)
  - Объём: запуск `doc-review` (3 итерации, профиль из `.claude/dev-conventions.json`) для тест-плана и плана до показа пользователю; результат итераций в ответе `flow`.
  - Готово, когда: цикл запускается кодом, а не агентом, недоступность Codex даёт `blocked` с причиной, а не тихий пропуск.

- [ ] C1 — Jira: команда transition (Jira: TBD) (est: 1–3д / agent: 0.5–1.5д)
  - Объём: команда `transition` в `plugins/kit/tools/jira/` (Playwright) для статуса «В работе»; по образцу `create`, с `--dry-run`.
  - Готово, когда: команда меняет статус реального тикета, повторный вызов безопасен, тесты и сценарии `scenarios/` обновлены.

- [ ] C2 — Стадии ticket и in-progress (Jira: TBD) (est: 0.5–1д / agent: 0.25–0.5д) (depends: A1, C1)
  - Объём: определение тикета (ветка, контекст, `ticketPrefix`, ссылка на задачу: `flow start` принимает и готовый id, и ссылку вида `https://jira.example.com/browse/ABC-123`, из которой берётся `ABC-123`), `needs-input` с предложением `jira-writer` при отсутствии ключа, вызов `jira transition`, `skip` с причиной при отказе пользователя.
  - Готово, когда: обе стадии работают по порядку, id берётся и из готового значения, и из ссылки (неподдерживаемая ссылка даёт `blocked` с причиной), всё покрыто тестами с заглушкой Jira.

- [ ] D1 — Skill polish (Jira: TBD) (est: 1–2д / agent: 0.5–1д)
  - Объём: переносимый skill `kit:polish` (проход по diff на упрощение и переиспользование, затем проход ревью на корректность, находки правятся без отчёта, итог сохраняется); мод `polish` вызывает этот skill.
  - Готово, когда: skill не зависит от встроенных команд Claude, мод остаётся рабочим, `claude plugin validate` проходит.

- [ ] E1 — Хуки Claude: мод task-flow (Jira: TBD) (est: 1–3д / agent: 0.5–1.5д) (depends: A3)
  - Объём: мод `mods/task-flow/` с `SessionStart` (печатает `flow status`), `Stop` (не даёт закончить ход посреди стадии без вопроса) и `PreToolUse` на `git push` и создание PR; запись в `marketplace.json` и `BASE_PLUGINS`.
  - Готово, когда: тесты мода и `claude plugin validate` проходят, при отсутствии `flow`-состояния хуки ничего не блокируют.

- [ ] E2 — Хуки Codex (Jira: TBD) (est: 1–2д / agent: 0.5–1д) (depends: A3)
  - Объём: те же проверки в хуках рядом с `plugins/pr-flow-codex/`; сохранить совместимость с существующим `hooks.json`.
  - Готово, когда: хуки проверены на тестах, работа без хуков не нарушена.

- [ ] E3 — Git-хук pre-push (Jira: TBD) (est: 1–2д / agent: 0.5–1д) (depends: A1)
  - Объём: хук `pre-push` в `rules/hooks/`, ставится `setup.sh`: отказывает, пока не закрыты `polish`, `local-test`, `review`; `pre-commit` не затрагивается.
  - Готово, когда: установка идемпотентна, существующие хуки не ломаются, отказ даёт понятное сообщение с `flow status`.

- [ ] F1 — Стадии implement, polish, local-test, review, pr (Jira: TBD) (est: 2–3д / agent: 1–1.5д) (depends: B1, B2, C2, D1)
  - Объём: `flow` ведёт стадии 6–10: согласие пользователя и метод реализации (`needs-input`), финальный verification pass, запуск skill `polish`, `testing-changes`, `plannotator review` кодом, запись URL PR после `pr-flow` и проверка forgejo CLI.
  - Готово, когда: задача проходит все 10 стадий на тестовом сценарии, закрытие стадии без доказательства невозможно.

- [ ] F2 — Переключение правил и роадмапа на flow (Jira: TBD) (est: 2–3д / agent: 1–1.5д) (depends: F1)
  - Объём: сжатие `rules/core.md` и `rules/orchestrator.md` до ссылки на `task-flow`, сокращение `document-approval.md`, `brainstorming.md`, `writing-test-plans.md`, `writing-plans.md` до правил содержания, шаги 4–5 `executing-checkpoints.md` на `flow start`, обновление `roadmap-state.json` из `flow`, блок в `AGENTS.md` через `build-agents-md.sh`.
  - Готово, когда: роадмап и одиночная задача идут через один цикл, работа вне задачи не сломана, все тесты кита и `claude plugin validate` проходят.

## Оценка

| Показатель | Вручную | С агентом |
|---|---|---|
| Сумма по шагам | 17–33д | 8.5–17д |
| Критический путь (depends) | 10–17д | 5–8.5д |
| Осталось (незакрытые шаги) | 16–30д | 8–15.5д |

Критический путь: A1 → A2 → B1 → B2 → F1 → F2. Допущения: исполнитель знает репозиторий и тестовую обвязку кита, Jira-сценарии C1 проверяются на реальном экземпляре, ожидание согласований не учтено.

## Сквозные риски

- Хуки Claude и Codex меняются независимо от кита; E1 и E2 проверять на актуальных версиях агентов.
- `plannotator` CLI и MCP-инструмент могут расходиться по поведению; B1 опираться на CLI как на общий для всех агентов.
- До F2 два режима (прежние правила и `task-flow`) сосуществуют; не допускать, чтобы `task-flow` противоречил `core.md`.

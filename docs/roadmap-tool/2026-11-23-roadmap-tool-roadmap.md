# Роадмап: Инструмент roadmap

## Контекст

Скилл `roadmap` описывает почти весь процесс текстом: какие шаги готовы и чем заблокированы, какие шаги уже идут в открытых PR, из какой ветки стартовать и как скрыть чужие роадмапы, как закрыть шаг (чекбокс, удаление файлов плана, статус, оценка), как пересчитать таблицу «Оценка». Агент выполняет это по тексту, поэтому результат зависит от того, что он вспомнит и как поймёт; фактическое время шага вообще не измеряется, `actualDays` приходится спрашивать у пользователя.

Цель — перевести в TypeScript-инструмент `plugins/kit/tools/roadmap/` всё, что можно сделать кодом, а агенту оставить только суждение: декомпозицию на шаги, диапазоны оценки, спеки и планы. Фактическое время считается автоматически из активности `flow`.

Ограничения: инструмент без зависимостей на Node 24, как `flow`, `forgejo` и `jira`; после каждого шага кит остаётся рабочим (скилл `roadmap` переключается на инструмент только вторым шагом); существующие роадмапы и `roadmap-state.json` остаются валидными; запись состояния шага из `flow` (F2) сохраняется и не конфликтует с инструментом.

Лимит шага для этого роадмапа и далее — 7 дней с агентом (`agent.max ≤ 7д`), по решению пользователя; он заменяет прежний потолок «3д вручную», правило в `roadmap/SKILL.md` обновляется вторым шагом. Допущения оценки: исполнитель знает репозиторий и тестовую обвязку кита, GitHub и Forgejo проверяются на заглушках, ожидание согласований не учтено; день — около 6 часов сосредоточенной работы, оценка с агентом включает проверку человеком и доработки.

## Целевое устройство

Инструмент `roadmap` с CLI `node <base>/../../tools/roadmap/cli/main.mts <команда>`; ответы — JSON с полем `result` (`ok`, `blocked`, `needs-input`) и `--text` для человека, как у `flow`.

| Команда | Что делает кодом |
|---|---|
| `validate [<slug>]` | Проверяет строки чек-листа (`est`, `depends`, потолок шага), согласованность markdown и `roadmap-state.json`, ссылки зависимостей, в том числе между роадмапами |
| `init <slug>` | Создаёт `roadmap-state.json` из чек-листа и заполняет таблицу «Оценка» |
| `estimate [<slug>]` | Пересчитывает `## Оценка` (сумма, критический путь, остаток) и теги `(est: …)` из состояния |
| `status [<slug>]` | Для каждого шага: готов, заблокирован (чем), в работе (в каком PR), можно начать стеком (от какой ветки); данные из `origin/<default>` и открытых PR (GitHub, Forgejo) |
| `pick <id>` | Создаёт ветку от правильной базы, скрывает чужие роадмапы (`git sparse-checkout`), заполняет `stepFolder`, печатает команду `flow start` |
| `close <id>` | Отмечает чекбокс, удаляет файлы плана и тест-плана, ставит `closed`, записывает `actualDays` из `flow`, пересчитывает «Оценку», удаляет завершённый роадмап, снимает изоляцию |
| `mark <id> --status <статус> [--spec <путь>]` | Переводит статус шага в Phase 2 (подготовка спек пакетом) |

Фактическое время: `flow` записывает в состояние задачи метки времени (старт, закрытие и пропуск стадий, сбросы); команда `flow time` суммирует интервалы между соседними метками, пропуская паузы длиннее порога (по умолчанию 3 часа, настраивается), и переводит итог в дни по 6 часов. `roadmap close` берёт значение оттуда; если данных `flow` нет, просит указать `--days`.

За агентом остаётся то, что кодом не решить: декомпозиция роадмапа и шагов, диапазоны оценки, дизайн-спеки, тест-планы и планы реализации, выбор метода реализации.

## Задачи

- [ ] A1 — Инструмент roadmap: validate, init, estimate, status, pick (Jira: TBD) (est: 9–14д / agent: 4.5–7д)
  - Объём: каркас `plugins/kit/tools/roadmap/` (`src/`, `cli/main.mts`, `test/`); разбор markdown-роадмапа (обе формы: «Шаги» и «Список задач») и `roadmap-state.json`; `validate` и `init`; `estimate`; `status` с наложением открытых PR (GitHub через `gh`, Forgejo через CLI кита) и стековыми шагами; `pick` с выбором базы, именем ветки по правилам проекта, изоляцией и заполнением `stepFolder`. Скилл `roadmap` на этом шаге не меняется.
  - Готово, когда: `validate` отклоняет шаг сверх лимита, битые теги и ссылки зависимостей; `status` на тестовых репозиториях верно различает готов, заблокирован, в работе и стековый шаг (в том числе межроадмапные зависимости); `pick` создаёт ветку от нужной базы и обратимо скрывает чужие роадмапы, не трогая пользовательский `sparse-checkout`; `estimate` воспроизводит текущие таблицы «Оценка» существующих роадмапов; всё покрыто `node --test` с заглушками `gh` и Forgejo; `claude plugin validate` проходит, скилл работает как раньше.

- [ ] B1 — Время, закрытие и переключение скилла на инструмент (Jira: TBD) (est: 6.5–11д / agent: 3.25–5.5д) (depends: A1)
  - Объём: метки времени в состоянии задачи `flow` (обратная совместимость со старыми файлами состояния) и команда `flow time` с отсечением пауз; `roadmap close` с автоматическим `actualDays`; `roadmap mark` для Phase 2; переписывание `roadmap/SKILL.md` и `references/` на вызовы инструмента (`status` → `pick` → `flow start` → `close`), так что в тексте остаётся только суждение агента; правило лимита шага меняется на `agent.max ≤ 7д`; описание «Кто обновляет состояние» согласуется с записью состояния из `flow` и командами `close` и `mark`.
  - Готово, когда: для задачи с реальной историей стадий `flow time` возвращает ожидаемые дни и игнорирует длинные паузы; `close` на тестовом роадмапе отмечает чекбокс, удаляет файлы плана, ставит `closed` и `actualDays`, пересчитывает «Оценку» и удаляет завершённый роадмап; тексты скилла не содержат процедур, которые делает инструмент; `tests/layout.test.mjs`, тесты инструмента, `flow` и `claude plugin validate` проходят.

## Сквозные риски

- Два автора записи `roadmap-state.json`: `flow` (продвигает статусы вперёд при работе с `--step-dir`) и `roadmap` (`close`, `mark`, `pick`). Оба пишут атомарно и не понижают статус; разграничение закрепляется в B1.
- Различия GitHub и Forgejo при наложении PR: паритет проверяется на заглушках обоих провайдеров, реальный прогон — на стадии локального тестирования A1.
- Состояние `flow` старого формата без меток времени: `flow time` отвечает «нет данных», `close` просит `--days` вместо выдуманного значения.

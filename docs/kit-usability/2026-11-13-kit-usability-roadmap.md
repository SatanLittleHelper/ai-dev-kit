# Роадмап: удобство использования AI Dev Kit

## Контекст

Цель — сократить путь от подключения кита к первой полезной задаче, сделать состояние установки понятным, а обновление предсказуемым. Здесь собраны все восемь направлений из обсуждения: диагностика, быстрый старт, единая команда, подготовка машины коллеги, обновление, памятка запросов, единый реестр и объяснения остановок агента. Обновление разделено на три самостоятельно поставляемых шага.

Сейчас есть `setup.sh`, установщики модов и внешних зависимостей, скилл обновления, правила и генератор `AGENTS.md`. Списки компонентов поддерживаются в нескольких местах. README подробно объясняет устройство кита, но пользователю нужен короткий путь к первой задаче. Исходная база — коммит `e53cdd5` и PR #89 с установкой Superpowers и Plannotator; перед реализацией сверить основную ветку.

Ограничения: сохранить существующие команды, пользовательские настройки и явные отключения компонентов; различать возможности Claude Code и Codex; после каждого шага кит остаётся работоспособным. Каждый пункт — отдельная задача, номера пока `TBD`. Имена новых команд предварительные. Спецификации, планы тестирования и реализации готовятся при взятии конкретного шага.

Оценки грубые: один разработчик, знакомый с репозиторием; день — около 6 часов сосредоточенной работы. Оценка с агентом включает проверку человеком и доработки. Ожидание внешних сервисов не учтено.

## Целевое устройство

Существующие установщики сохраняются, а поверх них появляется единая команда управления. Общий реестр задаёт состав компонентов. Диагностика проверяет состояние без изменений проекта; установка, подготовка машины и обновление дают согласованные отчёты. Короткий старт и памятка описывают повседневные сценарии. Откат покрывает явно определённые части состояния.

## Порядок выполнения

Начать с A1 и A2 — диагностики и отчёта установки. B1, B2 и F1 можно выполнять независимо. C1 подготавливает единый состав компонентов для C2, D1 и E1. Обновление развивается по цепочке E1 → E2 → E3. Порядок списка отражает приоритет, а `depends` — только обязательные зависимости.

## Задачи

- [ ] A1 — Диагностика doctor (Jira: TBD) (est: 1–3д / agent: 0.5–1.5д)
  - Объём: проверять подключение правил, наличие скиллов, установку плагинов, доступность CLI и актуальность блока `AGENTS.md`. Различать записанные настройки и подтверждённую работоспособность; непроверенное состояние обозначать явно.
  - Готово, когда: диагностика не меняет проект, показывает успешные проверки, предупреждения и ошибки, предлагает конкретные команды исправления и возвращает документированные коды завершения.

- [ ] A2 — Итоговый отчёт установки (Jira: TBD) (est: 0.5–1.5д / agent: 0.25–0.75д) (depends: A1)
  - Объём: после `setup.sh` показывать результаты по компонентам, оставшиеся проблемы, команды исправления и необходимость перезапуска агента; использовать общие проверки диагностики.
  - Готово, когда: успешная и частично завершённая установка дают понятный отчёт, ошибка компонента сохраняет ненулевой код завершения.

- [ ] B1 — Короткий стартовый раздел README (Jira: TBD) (est: 0.5–1д / agent: 0.25–0.5д)
  - Объём: вынести в начало README путь «установить → проверить → дать первую задачу», предусловия и ожидаемый результат. Подробное устройство оставить ниже. До появления новой команды использовать существующие рабочие команды.
  - Готово, когда: новый пользователь может пройти первый сценарий по началу README; инструкции ссылаются на существующие команды.

- [ ] B2 — Памятка повседневных запросов (Jira: TBD) (est: 0.5–1д / agent: 0.25–0.5д)
  - Объём: описать запросы «разбери задачу», «продолжи роадмап», «проверь изменения», «сделай PR»: результат, зависимости и возможные точки решения пользователя. Добавить ссылку из README.
  - Готово, когда: каждый сценарий содержит пример запроса и ожидаемые артефакты; различия поддержки Claude Code и Codex обозначены.

- [ ] C1 — Единый реестр компонентов (Jira: TBD) (est: 1–3д / agent: 0.5–1.5д)
  - Объём: свести метаданные скиллов, модов и внешних зависимостей в один источник для установки, обновления и диагностики. Обязательные форматы marketplace сохранить; производные списки генерировать либо проверять на соответствие.
  - Готово, когда: добавление компонента не требует ручного согласования независимых списков; установка, обновление и диагностика используют согласованный состав, существующие отключения сохраняются.

- [ ] C2 — Единая команда управления (Jira: TBD) (est: 1–3д / agent: 0.5–1.5д) (depends: A1, C1)
  - Объём: предоставить из потребляющего проекта действия `kit install`, `kit doctor`, `kit update`, `kit status` с общей справкой и понятными ошибками. Название `kit` рабочее; способ доставки и окончательное имя выбрать в спецификации.
  - Готово, когда: все четыре действия работают; `status` объясняет установленное состояние, `doctor` проверяет его; старые скрипты работают, README и памятка обновлены.

- [ ] D1 — Подготовка машины коллеги после клонирования (Jira: TBD) (est: 1–2д / agent: 0.5–1д) (depends: A1, C1)
  - Объём: отделить первичное подключение кита к проекту от подготовки машины для уже настроенного проекта. Восстанавливать локальные компоненты по состоянию проекта, сохранять отключения, завершать диагностикой и отчётом о необходимости перезапуска.
  - Готово, когда: в чистом окружении после клонирования документированный сценарий готовит машину; повторный запуск не создаёт дубликатов и сохраняет пользовательские настройки; ограничения агентов объяснены.

- [ ] E1 — Предварительный просмотр обновления (Jira: TBD) (est: 1–2д / agent: 0.5–1д) (depends: C1)
  - Объём: до применения показывать текущую и целевую версии, добавляемые и обновляемые компоненты, существенные изменения workflow. Отделить просмотр от применения.
  - Готово, когда: просмотр не меняет проект и установленные компоненты; объём обновления понятен; недоступность источника версии отображается явно.

- [ ] E2 — Отчёт о результате обновления (Jira: TBD) (est: 0.5–1.5д / agent: 0.25–0.75д) (depends: E1)
  - Объём: показывать результат по компонентам, изменения правил и workflow, оставшиеся действия и необходимость перезапуска; явно отражать частичный успех.
  - Готово, когда: отчёт различает обновлённые, пропущенные и неуспешные компоненты; повторный запуск позволяет завершить обновление, ошибки не подавляются.

- [ ] E3 — Возврат к предыдущему состоянию кита (Jira: TBD) (est: 1–3д / agent: 0.5–1.5д) (depends: E2)
  - Объём: определить границы отката версии submodule, управляемых блоков правил, настроек и версий компонентов. Сохранять необходимые сведения до обновления. Для внешних компонентов без поддержки отката сообщать ограничения заранее.
  - Готово, когда: поддерживаемые части предыдущего состояния восстанавливаются с сохранением пользовательских правок; неподдерживаемые действия перечислены до отката; частичный откат не выдаётся за полный.

- [ ] F1 — Понятные объяснения остановок агента (Jira: TBD) (est: 0.5–1д / agent: 0.25–0.5д)
  - Объём: унифицировать ответы при отсутствующей зависимости или необходимом решении: что мешает, какой шаг зависит от этого, как исправить и что можно продолжить. Исключить повторные запросы уже данного разрешения, сохранив обязательные согласования.
  - Готово, когда: правила и примеры покрывают отсутствие CLI, плагина, скилла и необходимого решения; сообщения короткие и содержат следующий конкретный шаг; независимая работа продолжается.

Критический путь: C1 → E1 → E2 → E3. Это расчёт при возможности параллельной работы; при одном исполнителе ориентир — сумма по шагам. Оценки пересматриваются после спецификации и плана каждого шага.

## Проверка результатов

Роадмап не меняет поведение кита. При реализации проверять успешные и неуспешные сценарии, повторный запуск, сохранение пользовательских настроек и совместимость существующих команд. Для документационных шагов сверять инструкции с доступными командами. Планы тестирования и реализации создавать перед началом соответствующего шага, а не заранее на весь роадмап.
